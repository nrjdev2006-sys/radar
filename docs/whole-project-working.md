# Zynq Radar Project — Detailed Working Guide

**Purpose:** describe the checked-in project and its tested digital Ethernet path, from the PC dashboard through the Zybo PS/PL design and back. This guide follows the source and generated hardware handoff in this repository. It separates current implementation from possible future radar hardware so the block diagram is not mistaken for a complete RF radar.

**Important scope:** the current board design has a Zynq PS, a PL pulse-gate/LED peripheral, and a PS-side UDP IQ detector. There is no AXI DMA, ADC capture path, RF transceiver, DAC, or antenna connection. The IQ window in the verified hardware test is generated by Python. Therefore `range_m` verifies packet transport and arithmetic, not a physical target measurement.

See the companion [whole-project block diagram](whole-project-block-diagram.md) for the detailed architecture drawings, AXI registers, packet sequence, and board indicators.

## 1. Current implementation at a glance

| Area | Present implementation | Does not currently do |
|---|---|---|
| PC dashboard | Local HTTP server, live I/Q signal generator, waveform/spectrum/derived plots, UDP sender, reply display | Capture an RF receive signal; configure the currently deployed PS image's detector by the sliders |
| Host packet codec | RDR1 version 1, CRC-32, sequence-correlated synchronous UDP requests | Reliable streaming, retransmission, or packet reordering |
| Board Ethernet | Zynq PS GEM0 with lwIP UDP port 5005 over the onboard PHY | Use a PL Ethernet MAC or AXI DMA |
| Packet processing | ARM Cortex-A9 firmware validates RDR1 and analyzes IQ in software | Process the IQ datagram in PL hardware |
| PL pulse hardware | AXI4-Lite control registers and a 100 MHz pulse gate with event LEDs | Capture ADC samples, calculate range, generate RF, or stream IQ through AXI-Stream |
| Board test | Synthetic TX-reference/echo window produces a returned sample index and range | Validate physical range to a target |

### What was verified on the hardware

The project checkpoint records a successful test on 2026-11-17: the PC sent `HELLO` and a 256-complex-sample `IQ_SAMPLES` frame to `192.168.1.10:5005`; the PS returned a detection with `echo_sample=40`, `echo_delay_s=2 µs`, and `range_m=299.792`. UART logs confirmed the callback, IQ analysis and reply submission; the PC RX counter increased. The test is an end-to-end **digital** check. The reply includes `hardware_capture:false`.

During the latest dashboard bring-up in this session the PC Ethernet adapter reported `Disconnected`, so no new FPGA reply was available at that moment. The dashboard still serves locally and can generate/plot/send attempts; it cannot show a board result until the Ethernet link is up. This live-link state can change when the cable/adapter changes.

## 3. Full signal and control paths

### 3.1 PC local dashboard

The dashboard listens only on `127.0.0.1:8765`; it is not an FPGA web server. The browser talks to the local Python process using HTTP:

| HTTP path | Method | Use |
|---|---|---|
| `/` | GET | Serves the dashboard page. |
| `/api/state` | GET | Returns stream status, counters, latest generated samples, settings and latest FPGA reply. |
| `/api/start` | POST JSON | Validates controls, resets session counters and starts the UDP streaming worker. |
| `/api/settings` | POST JSON | Validates and applies settings to the live PC signal generator while streaming. |
| `/api/stop` | POST | Sets the stream stop event. |

While running, the Python worker:

1. Opens the UDP client to the selected board host and port.
2. Sends `HELLO` once. If HELLO times out, it records the failure but keeps generating and attempting IQ frames so the local plots can still run while the board is offline.
3. Creates a 256-sample complex window. Noise is generated from the adjustable `noise_std`. It inserts a reference pulse at sample 0 and, when enabled, a synthetic delayed echo at `echo_delay_samples`. Pulse width, PRI, and echo amplitude also shape the window.
4. Publishes samples to `/api/state` so the browser can draw them, then encodes the same samples as signed int16 I/Q and sends `IQ_SAMPLES`.
5. Waits for a reply. A returned detection/noise result increments the reply count; a timeout increments the timeout count. It targets up to 10 frames/s when round-trip latency permits. If the board is offline, the one-second UDP request timeout reduces the effective plotted/send cadence.

The page shows the generated window, threshold view, residual-noise view and spectrum. “Threshold filtered” and “residual noise” are PC-computed display views, not separate buffers returned by the FPGA. The PC-side SIGNAL/NOISE classification is also computed locally using the current threshold and minimum-SNR slider values.

**Control meaning:**

- `noise_std`, pulse width, PRI, delay, echo amplitude and enable-echo change the synthetic PC IQ samples sent on subsequent frames.
- Threshold amplitude and minimum SNR drive the PC-side display and local classification.
- This dashboard version sends HELLO followed by IQ frames; it does not send the `CONFIGURE` message. The sliders therefore do not change the running PS detector's configuration. This is intentional compatibility behavior after the deployed ELF replied with `ERROR` to CONFIGURE during an earlier run. The checked-in `main.c` source has a CONFIGURE handler, so the source and the ELF used in that run may not be the same build; treat the board-loaded ELF as authoritative until it is rebuilt/reloaded and CONFIGURE is independently verified.
- Returned FPGA fields take precedence for the FPGA output area. The PC does not read LED pins; physical LEDs must be observed on the board.

### 3.2 Ethernet and PS receive path

For the documented direct-cable setup, the PC wired NIC and board share a `/24` network:

| Device | IPv4 address | Board MAC / notes |
|---|---|---|
| PC wired Ethernet | `192.168.1.100/24` | No default gateway required for the direct link. |
| Zybo PS GEM0 | `192.168.1.10/24` | Firmware MAC `00-0A-35-7A-01-10`. |
| UDP destination | `192.168.1.10:5005` | lwIP UDP PCB bound to `IP_ADDR_ANY`, port 5005. |

The Zybo Z7-10 PS GEM0 MAC connects to the onboard PHY through PS MIO 16–27 (RGMII); MDIO/MDC use MIO 52–53. The PC sends ordinary Ethernet/IP/UDP frames over the copper cable. The PHY link LED only says the physical Ethernet link negotiated; it does not prove the firmware received or accepted an RDR1 datagram.

The firmware foreground loop repeatedly calls `xemacif_input(&board_netif)`. lwIP delivers UDP data to `udp_receive`. The callback copies a pbuf into a fixed 1400-byte local buffer, frees the pbuf, checks packet length/magic/version/payload length/CRC, extracts the sequence, and dispatches the message. This is CPU/pbuf handling. **There is no AXI DMA transfer of UDP payloads into PL or DDR sample buffers.** The PS uses normal software-visible memory for its packet and analysis arrays.

### 3.3 IQ detection algorithm in the PS firmware

The `IQ_SAMPLES` payload holds interleaved signed `I,Q` 16-bit components. For each pair, the firmware calculates `mag2 = I² + Q²`, records the maximum absolute I/Q component, stores magnitude-squared values, and insertion-sorts a bounded copy to obtain the median noise-power estimate.

The threshold is the greater of:

1. The squared configured absolute component threshold, and
2. A noise-relative threshold derived from the median magnitude-squared value and the configured Q8 amplitude SNR ratio.

The firmware then scans for contiguous runs above that threshold. It reports a detection only when at least two regions are found and all of these checks pass:

- First region starts at sample 0 (the TX reference is expected at the start of the supplied window).
- Second region starts exactly at `cfg_echo_delay_samples`.
- Both regions have at least `cfg_pw_samples` above-threshold samples.
- The second region has a valid peak.

The range is calculated on the ARM core as:

```text
delay_s = (echo_start - tx_start) / 20,000,000
range_m = 299,792,458 × delay_s / 2
```

With the default echo sample 40 and a 20 MHz sample rate, delay is 2 µs and range is 299.792 m. This is the range encoded in the synthetic IQ array. It is not an RF propagation time measured by the board.

The firmware replies with `DETECTION` and a JSON payload on success. On no qualified pair, it returns `ACK` with `status=noise_only`. Malformed/unsupported requests can return `ERROR` JSON or may be dropped if the header/CRC itself is invalid. The response includes `hardware_capture:false` to mark that the source was a digital IQ window.

### 3.4 PS to PL AXI-Lite path

At startup, `main()` attaches the driver to the Vivado-generated `XPAR_RADAR_AXI_PULSE_0_BASEADDR`, writes PW and PRI into the PL registers, then writes START. The board preset build's generated `xparameters.h` and saved block design place the segment at `0x40000000`, range 4 KiB.

During IQ callbacks, firmware writes the three event registers as individual MMIO writes. The AXI path is:

```text
Cortex-A9 store/load
  → PS M_AXI_GP0
  → generated AXI interconnect/address decoder
  → radar_axi_pulse S_AXI (AXI4-Lite)
  → timing/control/event registers
```

The PL timing core uses the 100 MHz `FCLK_CLK0`. It checks `PW > 0` and `PRI > PW`, latches active values on START, produces a gate of exactly PW cycles, then starts the next gate every PRI cycles. STOP returns the core to idle. The wrapper counts `pulse_start` edges in a 32-bit pulse counter. The firmware's STATUS message reads the PL busy, configuration-error, gate and pulse-count registers.

The IQ detector itself does not connect to the pulse core except through event writes for LEDs. No echo delay, IQ sample or range register is written into the PL.

## 4. UDP protocol specification used by this project

### 4.1 Common frame

All multibyte fields are network byte order. The 16-byte fixed header is followed by payload and a 4-byte CRC-32 over the header and payload:

| Byte range | Width | Field |
|---|---:|---|
| 0–3 | 4 | ASCII magic `RDR1`. |
| 4 | 1 | Version `1`. |
| 5 | 1 | Type ID. |
| 6–7 | 2 | Flags; currently zero/reserved. |
| 8–11 | 4 | Sequence number. |
| 12–15 | 4 | Payload byte length. |
| 16 onward | variable | Message-specific payload. |
| final 4 | 4 | CRC-32 (same reflected polynomial as zlib/firmware). |

`radar_host.protocol.UDPClient` increments sequence IDs modulo 2³², sends one request at a time, requires the response source tuple to match the configured board IP and port, and checks response sequence and message type. It does not retry or maintain a sliding window.

### 4.2 Message types

| ID | Type | Current behavior |
|---:|---|---|
| 1 | `HELLO` | Empty request; firmware returns ACK JSON with `status=ready`, board IP and UDP port. |
| 2 | `CONFIGURE` | Current checked-in `main.c` expects exactly five uint16 values (10 bytes): threshold component, min-SNR ratio Q8, pulse width samples, PRI samples, echo delay samples. Bounds are checked. The currently restored dashboard does not send this type because its deployed ELF previously returned ERROR. |
| 3 | `START` | Defined in host enum/interface proposal; not handled by current firmware switch. |
| 4 | `STOP` | Defined in host enum/interface proposal; not handled by current firmware switch. |
| 5 | `STATUS` | Firmware returns PL busy, TX gate, and pulse count JSON. |
| 16 | `IQ_SAMPLES` | Payload length must be a multiple of 4; each sample has signed int16 I then Q. Firmware checks minimum and maximum sample count. |
| 128 | `ACK` | HELLO/STATUS/CONFIGURE success and `noise_only` IQ result. |
| 129 | `DETECTION` | Qualified two-region IQ result with derived values. |
| 255 | `ERROR` | Valid RDR1 request with an unsupported type or invalid CONFIGURE/IQ parameters. |

The host `docs/interface.md` describes a broader proposed interface. Treat that as protocol design background; the actual implemented PS switch cases in `main.c` are authoritative for this board app.

## 5. Configuration values and example calculations

| Parameter | Default | Conversion / purpose |
|---|---:|---|
| FPGA IPv4 | `192.168.1.10` | Static firmware address. |
| FPGA MAC | `00-0A-35-7A-01-10` | Static MAC in `main()`. A PC ARP entry must agree if one is pinned. |
| UDP port | `5005` | Board listener and host target. |
| IQ sample rate | 20 MHz | Fixed firmware constant. Sample period = 50 ns. |
| Dashboard samples/frame | 256 complex | IQ payload = 256 × 4 = 1024 bytes. |
| Pulse width | 4 IQ samples | 0.2 µs at 20 MHz. (PS firmware source default is 3 until CONFIGURE is applied.) |
| PRI | 128 IQ samples | 6.4 µs; PRF = 156.25 kHz. |
| Echo delay | 40 IQ samples | 2 µs round trip; idealized range = 299.792 m. |
| Echo amplitude | 0.42 normalized complex amplitude | Synthetic generator control, not a physical voltage. |
| Frame interval | 0.10 s target | Dashboard aims for up to 10 FPS; request/reply latency and link status determine actual rate. |
| PL pulse width | 10,000,000 clock ticks | 100 ms at 100 MHz; drives LED0. |
| PL PRI | 20,000,000 clock ticks | 200 ms at 100 MHz; 5 Hz TX gate repetition. |

Two different timebases are in use and must not be confused:

- PL TX gate timing is based on the 100 MHz FCLK clock and 32-bit tick registers.
- IQ detection/range arithmetic is based on the fixed 20 MHz sample-rate constant and the sample index in the PC-supplied payload.

The current firmware does not timestamp actual ADC conversions against `tx_gate`; the host input merely follows the expected convention that sample 0 is TX reference.

## 6. LED stage interpretation

| LED | Meaning | Expected observation during one test frame |
|---|---|---|
| LED0 | PL `tx_gate` | Pulses periodically after firmware startup, even without an Ethernet packet. |
| LED1 | An IQ frame reached the callback and was analyzed | One event for detection or noise-only. |
| LED2 | IQ matched the expected reference+echo pattern | Event only for a qualified detection. |
| LED3 | lwIP accepted the response for transmission | Event after a valid detection reply's `udp_sendto()` returns success. |

An LED event pattern is a short indicator, not a latched status bit. Each LED event sequencer ignores another event while active, so repeated high-rate packets may not create one visually separate blink per packet. A blinking LED0 alone proves only that PL startup pulse timing is running; it does not prove Ethernet reception. A Python reply is stronger evidence of the complete request/reply path.

The board LED mapping is set by XDC: LED0 M14, LED1 M15, LED2 G14, LED3 D18. The browser only shows reply-derived indicators; it cannot sense the LED outputs.

## 7. AXI DMA, memory and cache notes

The phrase “AXI DMA” is often used for a PS/PL high-volume data path, but **this repository does not currently instantiate one**. The design uses:

- `M_AXI_GP0` for CPU register accesses;
- `S_AXI` on the custom peripheral for AXI-Lite registers;
- CPU load/store instructions and lwIP pbufs for network payload handling.

It does not use `S_AXI_HP`/`S_AXI_ACP`, an AXI DMA IP, AXI-Stream, scatter-gather buffer descriptors, a PL sample FIFO, or a DMA cache-maintenance path. IQ analysis arrays (`magnitudes`, `sorted`) are local to the firmware callback's CPU stack. This keeps the current sample rate/packet test simple but makes it software processing, not PL acceleration.

A real ADC-to-PL/PS design would need a specified converter interface and clock, capture trigger, buffering, and ownership scheme. If AXI DMA is added, its memory mapping, descriptor rings, cache coherency, interrupt or polling model, maximum packet/capture dimensions and backpressure handling must be designed and validated. None of those design choices can be inferred from the current bitstream.

## 8. Build, load, and run commands

These are the checked-in project's Windows entry points. Tool paths depend on the local installation.

### 8.1 Vivado hardware handoff

The builder targets the Zybo Z7-10 `xc7z010clg400-1`, applies the Digilent board preset, enables PS GEM0 RGMII/MDIO, packages `radar_axi_pulse`, builds the wrapper/bitstream and exports an XSA:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\vivado\build_project.ps1
```

Open `fpga/vivado/radar_vivado_project/radar_vivado.xpr` to inspect the block design. The source `radar_system.bd` exposes DDR/FIXED_IO, the custom pulse peripheral and its four LED outputs. The current generated address segment is `0x40000000`, range 4 KiB.

### 8.2 Vitis PS application

Build the standalone PS application from the fixed XSA:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\vitis\build_vitis.ps1
```

Outputs used by the JTAG TCL are `fpga/vitis/radar_ps_build/radar_ps_app.elf` and the XSA-derived `ps7_init.tcl`/bitstream files under the Vivado project. The source should be built against the same XSA whose bitstream will be loaded.

### 8.3 JTAG load/run

Start `hw_server` on TCP port 3121, then run the checked-in XSCT TCL with the installed XSCT executable:

```powershell
& 'D:\Vivado\2024.2\xsct-trim\bin\xsct.bat' .\fpga\vitis\run_jtag_major.tcl
```

The Tcl resets A9 core 0, initializes PS7, downloads `radar_system_wrapper.bit`, downloads the PS ELF and continues the core. FPGA configuration and PS execution are volatile and must be repeated after power cycle. The script prints `MAJOR_BRANCH_RADAR_APP_RUNNING` when it reaches the final `con` command; UART output is the best boot/network diagnostic if a USB-UART COM port is available.

### 8.4 Direct Ethernet configuration

For direct PC ↔ Zybo cable:

1. Connect the PC wired adapter to the board Ethernet port.
2. Set the PC wired adapter to `192.168.1.100`, subnet mask `255.255.255.0`; no gateway is needed for this subnet.
3. Confirm the adapter reports **Up** and a negotiated link speed.
4. If a permanent neighbor entry is used, map `192.168.1.10` to `00-0A-35-7A-01-10` (not an old MAC from another app/firmware).
5. Internet access over USB/tethering can remain on a separate adapter; the UDP route to `192.168.1.10` must use the wired FPGA adapter.

If the PC Ethernet adapter is Disconnected, an ARP entry or disabled firewall cannot restore the physical link. Resolve cable/PHY/adapter state before interpreting UDP timeouts.

### 8.5 One-shot digital Ethernet test

From project root:

```powershell
py -3.11 -m radar_host.hardware_test --host 192.168.1.10
```

The sender constructs a 256-sample TX reference at sample 0 and a three-sample synthetic echo at sample 40, sends HELLO, sends IQ, checks the response type/sample count/peak/range, then prints PASS. For sample 40 at 20 MHz:

```text
echo delay = 40 / 20,000,000 = 2 microseconds
monostatic range = 299,792,458 × 2e-6 / 2 = 299.792458 metres
```

This validates the digital packet and calculation pipeline only. No RF is emitted by the LED gate, and no physical echo is measured.

### 8.6 Live dashboard

Run:

```powershell
py -3.11 -m radar_host.dashboard --host 192.168.1.10
```

Then visit `http://127.0.0.1:8765`, press **Start**, and inspect frames sent, FPGA replies, timeouts, returned status/range, and the four plots. The server runs on localhost; the FPGA link remains through the wired NIC. **Stop** ends the sender; Ctrl+C in the terminal stops the server.

For the current dashboard, the signal parameter sliders affect the generated PC IQ and local analysis. They are not hardware-register controls and this version intentionally does not send CONFIGURE packets. Do not interpret a local `SIGNAL` label as an FPGA detection; the “FPGA reply” and range fields must show a real received board UDP response.

### 8.7 Offline software checks

The repository includes these software test commands:

```powershell
py -3.11 -m unittest discover -s tests -v
```

These unit tests cover the host reference model and packet codec. They do not program hardware or verify cable/PHY/GEM operation. RTL timing/AXI testbenches are launched by the scripts documented in `fpga/README.md`; simulation likewise does not establish RF behavior.

## 9. Troubleshooting by layer

| Observation | What it establishes | Next check |
|---|---|---|
| LED0 periodic; no LED1 | PL pulse sequencer is running; no IQ callback observed | NIC link/IP/subnet/route, board IP/MAC, UDP port, app startup. |
| LED1 flashes; no LED2 | IQ callback ran; current frame did not meet the two-region detector test | Confirm payload length, TX sample 0, pulse widths, threshold/SNR values in firmware and `echo_sample` placement. |
| LED2 flashes; no LED3 | Detection path ran; reply submission may have failed or event not visible | UART send log, lwIP error, return route, ARP table and PC capture. |
| LED3 flashes; Python times out | `udp_sendto` was accepted by lwIP, but host reply was not observed | Check PC NIC route/MAC, adapter RX counters, Wireshark, IP/port/source filtering, and board/host subnet. |
| HELLO works; `CONFIGURE` returns ERROR | Ethernet/RDR1 path is alive; deployed firmware does not accept that configuration request or payload | Confirm loaded ELF matches checked-in `main.c`; current dashboard avoids CONFIGURE and sends IQ directly. |
| Local graph moves; replies remain zero | PC generator/page is working; no valid board response | Check wired link; the plot is not evidence of FPGA reception. |
| FPGA returns detection with range but `hardware_capture=false` | PC-generated digital samples were processed and returned | Do not describe it as real target ranging; capture/align real ADC samples first. |

## 10. Known boundaries and next engineering steps

1. **Use real receive samples:** add a compatible RF transceiver/ADC and define the receive sample clock and format. Capture a window with sample 0 aligned to `tx_gate` (or include a hardware timestamp/reference in the capture metadata).
2. **Decide where signal processing runs:** current detector is in Cortex-A9 C code. For PL acceleration, define AXI-Stream sample widths, framing, thresholds, buffering and an AXI DMA/memory/cache strategy before drawing that path as present.
3. **Match deployed image to source:** build one XSA/bitstream/ELF set, record hashes/build IDs, load the set, verify HELLO/STATUS, then verify CONFIGURE support against the actual ELF.
4. **Make dashboard detector controls truthful end-to-end:** once firmware version/configure semantics are confirmed, send CONFIGURE only to supported firmware and display the ACKed/applied values separately from local synthetic generator values.
5. **Validate LEDs physically:** use the documented pin mapping and observe event signals on board. The browser cannot read these signals unless firmware returns explicit event/status telemetry.
6. **Build a real measurement calibration:** account for TX/RX delay, RF/transceiver pipeline, ADC clock, cable delay and antenna/target geometry before treating sample-derived ranges as measurements.

## 11. Source-of-truth notes

Some earlier planning text describes AXI-Stream/DMA and RF capture as proposed architecture; those paragraphs describe a target architecture, not the current hardware. The `fpga/README.md`, `docs/architecture.md`, and `docs/interface.md` include historical/proposal material. For the present data path, use the Vivado block design, RTL modules, current `main.c`, the RDR1 codec and the final hardware checkpoint together.

The checked-in `main.c` includes a CONFIGURE handler, but the dashboard is kept HELLO+IQ compatible because a prior run of the restored ELF replied ERROR to the old dashboard's CONFIGURE request. Source-level support is not proof that the ELF presently loaded on the board contains that handler. Confirm the loaded executable before relying on configuration updates.
